# 要件

優先度：**M** = 必須（v1）、**S** = できれば v1、**C** = 後回し可。
各要件の詳細は括弧内のドキュメントを参照。

## 1. 目的と前提

- 個人用のローカルデスクトップアプリ。画像・音楽・動画を 1 つのライブラリで管理し、混ぜて再生する。
- 対象は macOS（Apple Silicon、macOS 26 以降）のみ。将来 Windows に広げる余地は残すが、v1 では考慮しない。
- 想定規模：アイテム 10 万件、ライブラリ容量 2TB まで。

## 3. 非機能要件

| ID | 要件（Apple M1 相当、SSD、リリースビルド） |
|---|---|
| NFR-01 | 10 万件のライブラリで、起動から操作可能まで 1.5 秒以内 |
| NFR-02 | 10 万件のグリッドを 60fps でスクロール（サムネイル生成済み） |
| NFR-03 | タグ 3 つの AND 検索が 50ms 以内、全文検索が 100ms 以内 |
| NFR-04 | 画像サムネイル生成が 50 枚/秒以上 |
| NFR-05 | 取り込みはディスク速度が上限になること（ハッシュ計算がボトルネックにならない） |
| NFR-06 | プレイリストのキュー生成が 1 万エントリで 50ms 以内 |
| NFR-07 | メモリ使用量が 10 万件表示中で 500MB 以内 |
| NFR-08 | 強制終了・電源断のあとでも DB とファイルが整合した状態に戻せる |
| NFR-09 | キーボードだけで主要操作ができる。VoiceOver で主要な要素が読み上げられる |
| NFR-10 | 外部への通信はダウンロード・キャプチャ・ツール更新のときだけ |

- **NFR-01 の更新後の初回**（M11 の決定 1）：新しい版の Kura で前の版のライブラリを初めて開くときの一度きりの作業（空きの確かめ・バックアップ・マイグレーション・作り方の指紋による作り直しの印）は NFR-01 の外とし、2 回目以降と分けて記録する（開いたことのログの `upgraded`。architecture.md §13）。2 回目以降は 1.5 秒を保つ。更新が 300ms を超えたら「ライブラリを更新しています」を出す。M11 の実測（10 万件）：更新後の初回 1.39〜1.43 秒（うち更新 0.86〜0.90 秒）、更新直後の 2 回目 0.39 秒、解析済みのライブラリ 0.40〜0.58 秒。
- **NFR-02・05 の測り直し**（M11）：解析済みの 10 万件（透過・ドット絵の事実があり、市松模様と最近傍の表示を含む）の自動スクロールは 60fps（p99 18ms、20ms 超え 0）。取り込みは台帳のトリガを足しても M10 と変わらない（35KB の JPEG 4,000 件で −2%、誤差の範囲）。
- **NFR-03 の素材のフィールド**（M11。透過・ドット絵・色数・レート・ビット・チャンネル・ラウドネス・ピーク・ループ・アニメ）：10 万件で、一致が数千件までの条件は一覧 0.6〜9.6ms・⌘K の件数 10〜24ms。一致が 6〜9 万件の広い条件は `-透過:あり` 43ms（件数 51ms）、`透過!=あり` 72ms（75ms）、`ドット絵:なし` 91ms（114ms）で、新しいフィールドに置いた 50ms の目安を超える（アニメを「格子の設定 ?? 解析のコマ」にしたあとの `アニメ:なし` 90〜93ms（98〜102ms）・`-アニメ:あり` 50〜51ms（67〜68ms）も同じ）。時間のほとんどは、数万件の 32 バイトのハッシュで items を引くところ（一致する事実の集合を作るだけなら 5ms）。**この広い条件は M12 で直す**（M11 の検証のあとのユーザーの決定 17。roadmap.md の M12）：台帳と版の表を触るときに items に台帳の整数の id（`blob_id`）を持たせ、事実の集合を整数で引く形にして 50ms 以内にする（見込み約 13ms）。M11 では実測と原因の記録にとどめる（ADR-161）。タグ 3 つの AND（0.5〜0.9ms）と全文検索（0.16〜19ms）は M11 でも目標の中。
- **NFR-04 の判定の範囲**（M11 の決定 2・3）：透明を保つため、png・apng・gif・webp・aseprite・psd・psb・svg はエンジンで読み、同時の確保を 256MiB までにする（NFR-17 の一括の予算で数える）。そのため、大きな透過 PNG の多いライブラリでは 50 枚/秒を下回りうる（2048² の透過 PNG だけで 31 枚/秒）。判定は、写真（JPEG）と PNG・スプライトの混ざった組（`kura-devtools assets --bench`）で行う（M11 の実測 105〜112 枚/秒）。
- **NFR-07 の範囲**（M11 の決定 2）：NFR-07 はライブラリの表示の分。解析とエンジンのサムネイルのジョブのメモリは NFR-17 の一括の予算（`Class::Bulk`）で数え（サムネイルの同時の確保は 256MiB まで、解析 1 件は min(予算/2, 1GiB) まで）、ジョブが動いている間の値は別に記録する。試聴の PCM（読んだ音声を 1 件だけ、使わなければ 60 秒まで覚える）とアニメの帯（16M 画素まで）は、作る・覚える間を対話の予算（`Class::Interactive`。待たない）で数える。M11 の実測：10 万件の表示 334〜339MB、ジョブが動いている間の最大 553MB（ジョブのあと 253MB に戻る）。
- **解析の長さの範囲**（M11 の決定 2 から決まる。検証 E4）：解析 1 件の上限 min(予算/2, 1GiB)（物理メモリ 8GB 以上なら 1GiB）と見積もり（値の 2 倍＋デコーダの作業領域。音声のデコーダは作業領域を値と同じに見積もるので値の 3 倍。値はフレーム数×チャンネル数×4 バイト）から、長い音声は読まずに解析できないもの（`too_large`）になり、波形・ラウドネス・ループ点・素材の事実が出ず、インスペクタの試聴もできない（プレーヤーでの再生はできる）。FR-ASSET-04・05 はこの長さまでで判定する。目安は形式によらず、44.1kHz ステレオで約 16.9 分、48kHz ステレオで約 15.5 分、96kHz ステレオで約 7.8 分、44.1kHz モノラルで約 33.8 分（長さをヘッダから正確に読めない MP3 は長さの上限で見積もるので、もっと短くても当たりうる）。指紋が変わるか利用者が頼む（`retry_analysis`）まで解き直さない。テスト `analysis::job::tests::long_audio_is_too_large_beyond_the_documented_length` が目安を見張る。M11 はこの範囲で受け入れ、**M13 で解析を区間ごとに読む形にして 1 件の上限を外す**（M11 の検証のあとのユーザーの決定 21。roadmap.md の M13。今は 1 件を丸ごと読んで値を持つので、長さに比例してメモリが要る）。
- **大きな確保を OS へすぐ返す**（ADR-163）：アプリは 1MiB 以上の確保を `mmap` で取り、解放したらすぐ OS へ返す確保器（`kura_mac::ReturningAllocator`）を使う。libmalloc のままでは、解析・サムネイルのジョブのあとも解放した大きな領域を抱えたままで（アプリ 588MB・合計 712MB）、NFR-07 に戻らなかった。
- **SVG を別のプロセスで読む**（M11 の決定 23。ADR-164。docs/editing.md §9.5）：SVG の形と値は、アプリ自身を引数付きで起動した子で読み、形 2 秒・値 10 秒を超えたら止める（サムネイルは種類の絵、解析は `too_large`。ジョブは先へ進み、ライブラリを閉じるのも待たせない：確認の S の形でジョブの途中に閉じて 14〜83ms）。子を起動する分だけ遅くなる（子の起動 1 回 約 5ms、SVG 1 件は p50 11.7ms。SVG だけの 1,084 件のサムネイルのジョブで 127 枚/秒、プロセスの中なら 745 枚/秒）が、NFR-04 の 50 枚/秒は保つ。子のメモリは NFR-07・NFR-17 の外で、入力の大きさ（16MiB）とエンジンの見積もり（文字・textPath・描く手間）だけで抑える（見積もりを通る確認の S2 の 4,000 枚は、止めるまでの 10 秒で 4.9GB。同時に描く数だけ重なる）。

編集（docs/editing.md §16）の目標。M10 の段 10 で測った（architecture.md §13 の M10 の実測、ADR-154）。

| NFR-16 | 同じ文書と同じ元からは、スレッド数・チャンクの切り方・経路（エディタ／一括）によらず同じ結果になる |
| NFR-17 | 編集のメモリが予算（既定は物理メモリの 1/4、上限 4GiB）を超えない。超える入力は落ちずにエラーになる |

- **判定の条件**（NFR-11〜17）：手元の Apple M4 Max で、プレビューのプールを 3 スレッドにしたものを「Apple M1 相当」とみなして判定する（4・16 スレッドも記録する）。NFR-13〜15 も一括のプールを 3 スレッドにして判定する。測るのは `kura-devtools bench edit`（p95 は最近順位法で、慣らし 10 回のあと 30 回。3 回の幅とロードアベレージを添える）。
- **エンジンの中**（NFR-11 の 25ms・NFR-12）：編集（文書かエディタの手）を受けてから、プレビューの値と変わったタイルの一覧ができるまで。出力のダイジェスト・エンコード・IPC・WebKit を含めない。NFR-11 の 50ms（画面に出るまでの全体）は M12 で測る。
- NFR-11 の 24MP の縮小の段は段 2（各軸 1/4）で判定する。
- **未達**（3 スレッド。理由は architecture.md §13）：
  - NFR-11 の音声の正規化の目標を変えるプレビュー：未達（5 分の曲で p95 38〜40ms。ラウドネスの解析はキャッシュに当たるが、目標の利得を求める計算が候補ごとに全ブロックを数え直す。操作そのものの時間で、16 スレッドでも p95 約 36ms）。
  - NFR-12 の全面の塗りつぶし（4096²）：未達（p95 33〜34ms。描く操作そのものの時間。4 スレッドなら p95 約 21ms、16 スレッドなら約 7ms）。
  - NFR-12 の 32px の筆のあとに最近傍 ×4 が続く文書（1024² → 4096²）：未達（p95 7.6〜8.0ms で、3 回のうち 1 回が 8ms を 0.04ms 超えた。境目。筆は差分で当て、下流の拡大は変わったタイルだけを描くが、32px の筆そのものが約 5.5〜5.9ms かかる）。8px は p95 約 2ms で達成。
- **NFR-07 と NFR-17 は別に数える**：NFR-07 はライブラリの表示の分。エディタで描いた値とノードのキャッシュは NFR-17 の予算で数え、エディタを閉じたら捨てる。
- NFR-17 の予算：物理メモリが分からなければ 2GiB。エディタを開いている間は min(1GiB, 予算/2) をエディタに取り置き、一括加工はその残りまでを使う（足りなければ待つ）。予算全体を超える要求は、描く前の見積もりでエラーにする。

## 4. 対象外（v1）

- Windows / Linux 版、モバイル版
- クラウド同期、複数ユーザー
- 動画の編集（画像・音声の編集は M12〜M14 で対象にした。ADR-133）
- 顔認識、AI による自動タグ付け
- App Store での配布
- ストリーミング配信（他の端末への再生）
- 操作の取り消し（⌘Z）の履歴。個々の操作の「元に戻す」の知らせはある（ADR-117）。エディタの中の取り消しは例外として入れる（FR-EDIT-06、ADR-141）
- 色での絞り込み（FR-SRCH-03 の色。ADR-117）
